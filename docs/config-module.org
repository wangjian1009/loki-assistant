#+TITLE: 配置模块设计
#+SETUPFILE: .setup.org

配置中心维护数据结构、校验、通用读写接口和提交事务。配置界面按元数据填写并提交数据。业务模块为监控点注册处理函数，由配置中心保存候选值和业务处理结果。

配置接口和编辑流程见 [[*字段级监控与完整编辑状态][字段级监控与完整编辑状态]]。

* 静态元数据

配置元数据函数通过 ~#[loki_config]~ 声明。该过程宏与 ~#[loki_api]~ 一样在编译期生成 ~linkme~ 注册项，服务组合根不执行运行时注册。元数据函数须为无参数、无泛型的同步函数，返回 ~ConfigModuleMetadata~ ；当前配置中心、控制中心、Emacs 和网络模块均采用这一方式。

#+begin_src rust
#[loki_services_macros::loki_config]
fn emacs_config_metadata() -> ConfigModuleMetadata {
    EmacsConfig::metadata()
}
#+end_src

配置项的 ~data_type~ 支持 ~string~、~password~、~integer~、~number~、~boolean~、~dictionary~、~structure~、~password_reference~、~list~、~file_path~ 和 ~executable~。~Executable~ 的值仍是 JSON string，允许完整路径或程序名。元数据还可声明默认程序名与建议搜索目录 (~search_paths~)；建议目录可以通过程序内常量静态定义，Emacs 模块使用 ~EMACSCLIENT_SEARCH_PATHS~ ，随模块元数据返回。

#+begin_src json
{
  "key": "emacsclient_path",
  "data_type": "executable",
  "remote_access": "local",
  "default": null,
  "executable": {
    "default_program": "emacsclient",
    "search_paths": ["/opt/homebrew/bin", "/usr/local/bin", "/Applications/Emacs.app/Contents/MacOS/bin", "/Applications/Emacs.app/Contents/MacOS"]
  }
}
#+end_src

没有用户设置和静态 ~default~ 时，配置模块按 services 启动时的 ~PATH~ 顺序搜索，再按 ~search_paths~ 的顺序补充查找。只接受实际可执行的普通文件（允许符号链接），返回绝对路径；不通过 shell，不执行待查找的程序，也不展开 ~ 和环境变量。每次读取重新查找，因此安装或移除程序后，下次读取即可反映变化。找不到程序时不生成默认值，Emacs 配置界面显示“未设置”并提供文件选择入口。

配置项通过 ~remote_access~ 声明绑定设备的访问范围。~local~ 为默认值，~read~ 开放读取。写入须同时得到 API 的 ~paired~ 声明与配置项的 ~read_write~ 声明授权，预检同样需要写权限。配置中心依据 network 注入的 Axum 请求扩展判断请求来源。远端元数据和生效值只包含可读项，直接访问受限项返回 403 ~remote-config-forbidden~ 。目前 ~network/relay_url~ 和 ~control-center/center_auto_start~ 对绑定设备只读，其余配置项仅限本机。

* 生效值与来源

~GET /data/{module_id}~ 中的每个值包含 ~value~ 和 ~source~ ：

#+begin_src json
{"module_id":"emacs","values":{"emacsclient_path":{"value":"/opt/homebrew/bin/emacsclient","source":"default"}}}
#+end_src

~GET /data/{module_id}/{key}~ 以及写入成功的响应保留模块和配置项标识，同时返回 ~value~ 与 ~source~ ：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","value":"/opt/homebrew/bin/emacsclient","source":"user"}
#+end_src

~source~ 只支持 ~user~ 与 ~default~。显式设置的值优先，即使与默认值相同也标记为 ~user~；否则返回静态默认值或发现的程序路径，并标记为 ~default~。未设置且没有默认值的项不出现在模块数据中，单项读取返回 404 ~config-not-set~。默认值中的 ~false~、~0~ 或空字符串均是有效值，不按真假判断是否存在。

~PUT~ 和 ~POST~ 的请求体仍为原始 JSON 值，不接收来源包装。字典合并或列表追加以当前生效值为基础，包括默认值，完成后整项标记为 ~user~ 。变更订阅只通知用户写入，自动发现的默认值不触发用户配置变更。

* 统一校验

~POST /config/validate~ 接受模块、配置项和待校验值，供客户端或其他程序使用：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","value":"emacsclient"}
#+end_src

接口与配置保存共用校验实现。整数配置可通过元数据 ~integer_range~ 声明包含上下界的取值范围。~Executable~ 检查目标存在、是普通文件并具有执行权限，允许指向普通文件的符号链接。程序名先按服务进程 ~PATH~，再按元数据 ~search_paths~ 查找；有效值规范化为绝对路径。整个检查不会执行目标程序。

校验通过时返回 HTTP 200 与规范化后的值：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","valid":true,"value":"/opt/homebrew/bin/emacsclient"}
#+end_src

配置值无效时仍返回 HTTP 200，使用 ~valid: false~ 和错误说明表示预检结果：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","valid":false,"error":{"source":"business","code":"invalid-config","message":"配置值无效：emacsclient 位置：文件不存在：/missing/emacsclient"}}
#+end_src

不存在的模块或配置项返回 404；内部错误使用对应 HTTP 错误码。预检不写入文件、不更新用户值，也不发出变化通知。~PUT /editing/{module_id}/{key}~ 与部分更新会在提交时重新校验；校验失败返回 400 ~invalid-config~，已有内存值、YAML 文件与变化通知均不受影响。~Executable~ 保存成功时使用规范化后的绝对路径。预检通过不保证提交时仍有效，例如文件可能在两次请求之间被移除。

Emacs 配置界面以 Customize 风格的 widget 按模块展示名称、说明、类型化编辑控件及来源状态，按服务端结果将错误标红并保留输入。校验、逐项保存、批量保存、撤销编辑和刷新行为见 [[file:emacs.org::*服务配置管理][服务配置管理]]。托盘“设置”调用 ~POST /emacs/apps/open?app=config~ ，由 services 的 Emacs 模块打开并聚焦配置界面。登录启动由控制中心的配置通知接入点处理。

* 文件写入

用户配置保存在 ~~/.assistant/config.yml~ 。首次成功写入时创建，后续写入用权限为 ~0600~ 的同目录临时文件原子替换。配置中心在落盘成功后更新内存和发布生效变更。写入失败返回 ~500 config-storage-error~ 。HTTP 请求断开后，已接受的事务继续执行。服务启动时校验已登记的值，并保留文件中其他版本或插件的未登记配置。

* 结构化配置

~GET /meta~ 的 ~modules[].items~ 描述配置值。~data_type: structure~ 表示单个结构。~data_type: list~ 表示数组，~list.item_type~ 声明数组元素类型。元素类型为 ~structure~ 时，~structure.fields~ 声明每个元素的字段类型、必填项、候选、校验器和可选默认值模板。配置界面按这些定义生成表单。~id_field~ 可指定数组元素的主键，以便单独保存元素。没有主键的数组通过通用 ~POST /editing/{module}/{key}~ 追加元素，界面按 ~label_field~ 显示条目标题。

结构可声明 ~show_all_fields~ ，让 Emacs 在一条记录下显示所有字段。缺少值时显示「未设置」，密码字段显示保存状态。

校验器可声明 ~emacs_pattern~ ，用于 Emacs 本地输入格式提示。服务端保存时按 ~checker.pattern~ 和对应的业务规则处理。

配置项可声明 ~requires_local_auth~、~save_timeout_seconds~ 和 ~read_only~ 。只读配置项可查询生效值，通过配置 HTTP 接口提交写入、删除或写入预检时返回 ~403 config-read-only~ 。配置中心按模块 ID 和配置键合并 ~CONFIG_ITEMS~ 注册的元数据。客户端按字段声明填写必填值，并显示服务端返回的保存结果。

| 操作 | 请求 | 结果 |
|------+-------+------|
| 读取配置定义和值 | ~GET /meta~、~GET /data/{module}~ | 读取注册的结构和生效值 |
| 新增带主键记录 | ~PUT /editing/{module}/{key}/{instance}~ 配合 ~If-None-Match: *~ | 返回 ~200~ 和保存记录，主键已存在时返回 ~412 config-record-exists~ |
| 修改带主键记录 | ~PATCH /editing/{module}/{key}/{instance}~ | 合并指定字段，按通知结果返回 ~200~ 或 ~202~ |
| 删除带主键记录 | ~DELETE /editing/{module}/{key}/{instance}~ | 返回 ~204~ 。记录已不存在时同样返回 ~204~ |
| 追加无主键元素 | ~POST /editing/{module}/{key}~ ，请求体是数组 | 返回保存后的完整数组 |
| 修改或删除无主键元素 | ~PUT /editing/{module}/{key}~ ，请求体是替换后的数组 | 返回保存后的完整数组 |

按字段修改和手动重试的契约见 [[*读取与提交][读取与提交]]。

* 命名类型、引用与补全

模块通过 ~types~ 声明可复用的值类型。标量字段在 ~data_type~ 中使用 ~{ref: module.type}~ 引用类型，列表在 ~list.item_type~ 中使用同样的引用。枚举类型由 ~enum~ 声明固定候选。记录引用类型通过 ~reference.target~ 指定目标集合，通过 ~key_field~ 指定保存的键，通过 ~label_field~ 指定搜索和显示的字段。目标字段在集合元数据中分别对应 ~id_field~ 和 ~label_field~ ，两者可以指向同一个字段。

#+begin_src yaml
id: llm
types:
  protocol:
    data_type: string
    enum: [codex, claude]
  client_id:
    data_type: string
    reference:
      target: llm.clients
      key_field: id
      label_field: name
  provider_id:
    data_type: string
    reference:
      target: llm.providers
      key_field: id
      label_field: id
#+end_src

~monitoring_filter~ 中三个列表分别引用 ~llm.protocol~ 、 ~llm.client_id~ 和 ~llm.provider_id~ 。客户端绑定中的标量 ~upstream~ 也引用 ~llm.provider_id~ 。

#+begin_src yaml
# monitoring_filter.structure.fields
- key: protocols
  data_type: list
  list:
    item_type: {ref: llm.protocol}
- key: clients
  data_type: list
  list:
    item_type: {ref: llm.client_id}
- key: upstreams
  data_type: list
  list:
    item_type: {ref: llm.provider_id}

# clients.structure 中的绑定字段
- key: upstream
  data_type: {ref: llm.provider_id}
#+end_src

LLM 客户端的 ~id~ 使用现有令牌携带的 UUID，以可编辑的 ~name~ 为显示名称。重名候选附带对应的 UUID。客户端改名后，历史用量和监控过滤器继续按原 UUID 关联。现有客户端记录由令牌提取 ~id~ 。

供应商以 ~id~ 作为主键和显示值，创建时填写，创建后固定。客户端绑定和监控过滤器都保存供应商 ID。

配置中心、快捷设置和 YAML 编辑器共用同一份模型。枚举补全取 ~enum~ 的值，记录引用补全按 ~label_field~ 搜索、插入 ~key_field~ 。~GET /config/options/{module_id}/{type_name}~ 返回已生效记录的 ~key~ 和 ~label~ 。配置中心显示引用对应的名称，点击字段值可重新选择。找不到对应记录时，以原键作为显示值。直接编辑 ~~/.assistant/config.yml~ 时，Emacs 自动启用 ~loki-assistant-config-yaml-completion-mode~ ，在 YAML 块字段及行内列表的命名类型值上按 ~TAB~ 补全。同文件的记录候选从当前缓冲区提取。

客户端集合声明 ~generate_id~ 。~POST /editing/llm/clients~ 接受 ~name~ 和 ~upstream~ ，配置中心生成 UUID 后返回新记录。已有记录通过 ~PATCH /editing/llm/clients/{id}~ 更新。旧版 v2 配置可在 services 停止后用新版 ~loki-services migrate-llm-client-keys~ 一次性补齐 UUID，命令会在写入前备份原文件。

例如在 ~modules.llm.monitoring_filter.upstreams~ 下输入供应商 ID 的一部分，补全后写入完整 ID。YAML 中实际保存的过滤条件形如

#+begin_src yaml
modules:
  llm:
    monitoring_filter:
      protocols: [codex, claude]
      clients: [1c30befd-aacd-419b-b0f3-8d72680d275b]
      upstreams: [work]
#+end_src

* 结构中的密码字段

带主键的结构数组可使用 ~Password~ 类型。~data_type.password.path~ 是 pass 内相对的 ~.gpg~ 路径，~{key}~ 展开为当前记录的主键值。省略 ~data_type.password.key~ 时，该字段是首行的主密码。指定 ~key~ 时，该字段对应后续的同名行。配置和 HTTP 响应只保存条目引用。

#+begin_src json
[
  {"key":"token","data_type":{"password":{"path":"loki-assistant/slack/{key}.gpg"}}},
  {"key":"d_cookie","data_type":{"password":{"path":"loki-assistant/slack/{key}.gpg","key":"d_cookie"}}}
]
#+end_src

配置模块将共享条目的候选凭据保存为一份加密条目。新记录可以按任意顺序填写字段，首次保存即使用按主键展开的文件名。正式条目已存在时，候选文件在独立目录中沿用同一文件名。业务确认后，配置模块更新正式条目和配置引用，并清理独立目录中的候选文件。修改一项时保留同一条目中未修改的字段。显式清除首行字段会删除整份共享条目和各字段的引用。配置写入失败时，配置模块尝试恢复原条目。

* 字段级监控与完整编辑状态

配置中心负责按元数据校验、分组、保存编辑值、投递变更和记录业务处理结果。业务模块提供监控处理函数，决定何时确认编辑、报告错误以及清除错误。普通配置保存后立即生效。有监控点的字段先保存为待确认，业务读取和生效变更订阅使用已确认值。

** 元数据与分组

模块元数据声明 ~monitors~ 。配置项和结构字段分别通过可选的 ~monitor~ 引用所属模块内的一个监控点。多个字段引用同一个 ID 时合并提交。模块级监控点可以横跨顶层配置项及单个结构的字段。记录级监控点归属于一个配置项，按记录主键分组。同一监控点在两个工作区上的编辑分别处理。

#+begin_src json
{
  "id": "slack",
  "monitors": [
    {"id": "team", "name": "Slack 工作区", "scope": "record", "item": "teams"}
  ],
  "items": [
    {
      "key": "teams",
      "data_type": "list",
      "lifecycle_monitor": "team",
      "structure": {
        "id_field": "team_id",
        "fields": [
          {"key": "team_id", "data_type": "key", "required": true},
          {"key": "name", "data_type": "string", "monitor": "team"},
          {"key": "token", "monitor": "team"},
          {"key": "d_cookie", "monitor": "team"}
        ]
      }
    }
  ]
}
#+end_src

示例省略部分已有属性。Rust 模块沿用静态配置注册，处理函数在服务组合时按 ~(module_id, monitor_id)~ 注入，元数据向客户端公开 ID、名称和作用范围。构造配置中心时检查引用、处理器和作用范围是否匹配。主键用来定位记录，创建后固定。需要按元素字段监控的列表声明稳定主键。无主键列表可以作为整项监控。

记录新增和删除由 ~lifecycle_monitor~ 负责，创建时该处理器收到完整候选记录，删除时收到已生效记录和删除意图。新增待确认时整条记录仅出现在编辑视图，继续填写字段会提交同一记录的完整候选。待删除记录保留在生效视图，编辑视图标记为「待删除」。生命周期确认提交整条记录的新增或删除，日常修改按各字段的 ~monitor~ 分组。

** YAML 存储

文件显式声明 ~format_version: 2~ 。~modules~ 按现有模块、配置项和记录结构组织。普通字段存原始值。有监控点的字段存 ~accepted~ 和 ~editing~ 。两个槽位各自记录 ~revision~ 和 ~value~ ，其中 ~value~ 可以是显式的 ~null~ 。空的 ~accepted~ 表示没有已确认的用户值，读取时按原规则使用默认值。空的 ~editing~ 表示没有待确认的编辑，带 ~revision~ 的 ~{remove: true}~ 表示候选操作为移除用户值。~_system~ 存放内部条目。

#+begin_src yaml
format_version: 2
modules:
  slack:
    teams:
      - team_id: TDEMO
        team_name: 示例工作区
        name:
          accepted: {revision: 7b217e7c-146c-45f7-95bc-56584179277e, value: 旧名称}
          editing: {revision: 509b6a1d-9fa6-41dc-9326-36b15f79ce7c, value: 新名称}
        token:
          accepted: {revision: 7b217e7c-146c-45f7-95bc-56584179277e, value: loki-assistant/slack/TDEMO.gpg}
          editing: {revision: 509b6a1d-9fa6-41dc-9326-36b15f79ce7c, value: loki-assistant/slack/pending/509b6a1d-9fa6-41dc-9326-36b15f79ce7c/TDEMO.gpg}
        d_cookie:
          accepted: {revision: 7b217e7c-146c-45f7-95bc-56584179277e, value: loki-assistant/slack/TDEMO.gpg}
          editing: {revision: 509b6a1d-9fa6-41dc-9326-36b15f79ce7c, value: loki-assistant/slack/pending/509b6a1d-9fa6-41dc-9326-36b15f79ce7c/TDEMO.gpg}
monitor_states:
  slack:
    - monitor: team
      instance: TDEMO
      item: teams
      revision: 509b6a1d-9fa6-41dc-9326-36b15f79ce7c
      status: failed
      error_revision: 509b6a1d-9fa6-41dc-9326-36b15f79ce7c
      error:
        code: slack-auth-failed
        message: 工作区凭据校验失败，请更新令牌和 Cookie。
_system: {}
#+end_src

监控状态的唯一键为 ~(module_id, monitor_id, instance)~ 。模块级监控没有 ~instance~ 。同组当前候选字段和监控状态共享本次处理的 ~revision~ 。业务确认后，已转入 ~accepted~ 的值保留该版本。状态包含 ~pending~ 、 ~processing~ 、 ~failed~ 和 ~accepted~ 。候选记录新增或删除时在同组状态上记录 ~record_operation: create|delete~ ，用于控制两个视图的记录可见性。~error~ 保存业务模块提供的 ~code~ 、 ~message~ 、可选的字段路径及其所属版本，整组只存一份。新编辑可以先前进到新版本，再由业务明确处理上一版错误。

沿用现有密码库事务。密码槽位只保存加密条目引用，已确认与编辑中的凭据分别从各自的条目解析。共享同一密码条目的字段共同保存候选条目，保留未编辑的行。业务确认后切换正式条目及配置引用，失败后保留候选密文供后续编辑。业务可通过结果 API 明确撤销指定的候选凭据，已确认的凭据继续可用。HTTP 和 Emacs 仅展示设置状态及变更，凭据值和条目路径均留在服务内部。

** 读取与提交

| 操作 | 响应或行为 |
|------+------------|
| ~GET /data/{module_id}~ 和 ~GET /data/{module_id}/{key}~ | 返回原有的生效配置结构，配置值仍由 ~value~ 和 ~source~ 表示。 |
| ~GET /editing/{module_id}~ | 返回一个模块的完整编辑快照，对应 YAML 中的模块数据和监控状态。 |
| ~PUT~ 、 ~POST~ 、 ~PATCH~ 、 ~DELETE /editing/{module_id}/{key}~ | 沿用原有的单项写入语义。 |
| ~PUT~ 、 ~PATCH~ 、 ~DELETE /editing/{module_id}/{key}/{instance}~ | 沿用原有的记录新增、修改和删除语义。 |
| ~PATCH /editing/{module_id}~ | 在同一请求内提交跨项修改，保存模块的整体修改时由 Emacs 使用。 |

~GET /data~ 下的接口优先返回已确认的用户值，其次按原规则解析默认值，包括运行时查找可执行文件。模块读取省略没有生效值的配置项，单项读取返回 ~404 config-not-set~ 。配置值保持原有标量、字典或记录数组的形状。候选值、版本、处理状态及错误通过 ~GET /editing/{module_id}~ 查询。

Rust 业务代码继续使用 ~ConfigService::value~ 、 ~module_values~ 、 ~read_record_with_passwords~ 和 ~read_record_passwords~ 。这些入口保留现有签名、返回结构、默认值解析和缺值行为。配置中心把持久化模型解析成原有 ~ConfigValue~ 和记录，普通业务调用读取已确认值和对应凭据。~subscribe_module~ 在生效值提交后发送原有结构的变更事件。监控处理函数通过该次请求的句柄获取候选快照。

~GET /editing/{module_id}~ 的 ~data~ 对应 YAML 的 ~modules[module_id]~ ，~monitor_states~ 对应 ~monitor_states[module_id]~ 。普通字段返回原始值，受监控字段返回完整的 ~accepted~ 和 ~editing~ 槽位，含各自的版本。模块没有用户设置时返回空 ~data~ 。默认值由 ~GET /data/{module_id}~ 解析。响应范围是模块注册的配置，密码槽位保留版本和操作，值用设置状态表示。

配置写入统一使用 ~/editing~ 下的路径。跨项 ~PATCH~ 请求体使用 ~changes~ 数组，每项包含 ~path~ 、 ~operation~ ，设置时另带 ~value~ 。结构字段路径为 ~[key, field]~ ，带主键记录的字段路径为 ~[key, instance, field]~ 。记录新增或删除使用记录路径及对应操作。路径与操作按元数据校验。批量写入逐项执行现有写入权限和本机鉴权。编辑快照供本机查询，远端读取继续按现有字段权限过滤已确认值。

一次请求中，每个监控组对修改后的完整候选快照执行一次处理，包括该组以前保存的编辑和未改动的有效值。局部更新基于已有编辑值，没有编辑值时使用生效值。完成格式、类型和权限校验后，配置中心在同一事务里写入普通字段和所有候选编辑，再入队处理。包含待确认编辑的请求返回 ~202~ 及相应版本，普通字段此时已生效。格式或类型校验错误沿用 HTTP 错误模型，写入前返回。业务处理成功或失败由后续编辑视图反映。

** 业务结果与重试

- 处理函数收到监控点、实例、~revision~ 、本次变更字段、已确认和候选快照。业务只通过此处理请求携带的句柄调用结果 API，结果写入范围限定为对应监控组和版本。
- 业务通过内部响应确认当前版本。~200~ 或 ~204~ 将该版本的编辑值转入 ~accepted~ ，同时清理错误。业务也可返回 ~NotificationConfirmedFields~ ，配置中心校验并一并写入派生字段。业务通过 ~NotificationValidationError~ 报告失败，配置中心保留候选以及业务错误。~202~ 保留待确认状态。
- ~set_error~ 之后，修改该组的配置会生成新版本并重新投递。若修改后的值碰巧等于生效值，只要与此前编辑值不同，也需要重新处理。旧错误保留到业务明确替换或清理。其他组的写入和界面刷新无需调度该组。
- 同一组串行处理，新保存的编辑可在该组排队。旧版本的结果无法应用到新版本。有外部状态的处理器在确认落盘后切换活动状态，或在接受失败时回退处理期间的外部操作。不同组可并行处理。进程重启后恢复未完成的待确认和处理中版本，业务按版本识别重复投递。已报告失败的版本等待编辑。存储或投递失败按配置基础设施错误处理，由配置中心保持可恢复的待确认版本。

控制中心模块处理 LaunchAgent 并报告失败。网络模块用候选地址验证中转配置，成功确认后切换活动连接，注册失败时保留原连接并报告监控错误。Slack 和 LLM 模块各自决定凭据、工作区和供应商是否有效，以及写入哪些业务派生字段。配置中心只执行上述通用事务。

** Emacs 原地编辑

每条记录直接在配置页显示可编辑 widget，同一个字段位置用于浏览、录入、保存和修正。未修改时显示有效值，修改后在字段所在行显示「生效值 → 当前输入」及状态。没有当前生效值时显示「未设置」。本地输入尚未保存时显示「未保存」，服务器已存候选后显示「待确认」或「处理中」。输入与服务器候选不同且两者都存在时，同时显示「已提交」和「当前输入」。记录新增在原列表中插入可编辑行，记录删除在原行展示状态。

#+begin_example
示例工作区 [TDEMO]
  本地显示名称   旧名称 → [新名称             ]
  用户令牌       已设置 → 已更换  [           ]
  Cookie d       已设置 → 已更换  [           ]
  处理失败 · Slack 工作区
  工作区凭据校验失败，请更新令牌和 Cookie。
  [保存修改]  [撤销未保存输入]
#+end_example

错误按监控组展示一次，并按 ~error.fields~ 标记关联字段。密码用「已设置」「已更换」「待移除」等状态表达前后差异。本地格式错误标在相应输入上。重提期间若错误来自前一版，标为「上次处理失败」并同时显示当前处理进度。业务清理错误后，该信息随最新快照消失。

保存一项、记录或模块时，收集相应范围的所有已修改字段并向 ~/editing~ 发出一次请求。保存中仍可继续输入，响应用于推进已提交基线。只要当前输入未随同该次请求提交，就保留为本地修改。刷新读取 ~GET /editing/{module_id}~ ，从服务端重建已确认值、已提交编辑和错误，并保留本地尚未提交的输入。没有已确认值时，使用 ~GET /data/{module_id}~ 返回的 ~source: default~ 值作为显示基线。编辑页可在有处理中版本且 buffer 可见时定期读取状态，收到确认后将新生效值显示在原位置。关闭页面停止查询。

** 一次性转换与切换

用新元数据逐项转换现有 YAML 中已保存的用户值。受监控字段的旧值直接进入带初始版本的 ~accepted~ ，~editing~ 置空。普通字段、未知用户配置及 ~_system~ 内部数据原样带入对应位置，缺失的值继续由默认值规则解析。

| 现有配置 | 转换后的监控 |
|----------+--------------|
| ~control-center/center_auto_start~ | 模块级 ~login-startup~ |
| ~network/relay_url~ | 模块级 ~relay~ 。中转令牌继续从现有密码库读取。 |
| ~slack/cache_retention_days~ | 模块级 ~cache-retention~ |
| ~slack/teams~ 和 ~slack/nicknames~ | 分别为记录级 ~team~ 和 ~nickname~ ，按各自读写字段的声明包装。 |
| ~llm/providers~ 和 ~llm/clients~ | 分别为记录级 ~provider~ 和 ~client~ ，按各自读写字段的声明包装。 |

如有旧 ~_pending_config_notifications~ ，按记录及字段拆成候选槽位，保留请求操作、候选密码引用及错误。用旧记录的已确认值比较候选，输出到对应监控组；旧的整条记录新增或删除写入生命周期监控。快照中检查过的本机配置没有待确认记录。

切换时先停止 services，执行新版 ~loki-services migrate-config~ 。该命令备份旧文件并将转换结果写入同目录临时文件。校验新文件及已确认值的投影与旧生效配置一致后，以 ~0600~ 权限原子替换，随后启用配套的 services 和 Emacs。Emacs、Slack 工作区配置页及其他配置写入调用方一并切换到 ~/editing~ 。正常启动只接受新格式。转换过程仅处理文件和加密引用，已迁入 ~accepted~ 的值直接作为启动配置加载。
