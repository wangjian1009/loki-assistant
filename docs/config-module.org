#+TITLE: 配置模块设计
#+SETUPFILE: .setup.org

配置中心维护数据结构、校验、通用读写接口和提交事务。配置界面按元数据填写并提交数据。业务模块可以在配置项元数据中声明通知接入点，由配置中心发出变更通知并确认处理结果。

* 静态元数据

配置元数据函数通过 ~#[loki_config]~ 声明。该过程宏与 ~#[loki_api]~ 一样在编译期生成 ~linkme~ 注册项，服务组合根不执行运行时注册。元数据函数须为无参数、无泛型的同步函数，返回 ~ConfigModuleMetadata~ ；当前配置中心、控制中心、Emacs 和网络模块均采用这一方式。

#+begin_src rust
#[loki_services_macros::loki_config]
fn emacs_config_metadata() -> ConfigModuleMetadata {
    EmacsConfig::metadata()
}
#+end_src

配置项的 ~data_type~ 支持 ~string~、~password~、~integer~、~number~、~boolean~、~dictionary~、~structure~、~password_reference~、~list~、~file_path~ 和 ~executable~。~Executable~ 的值仍是 JSON string，允许完整路径或程序名。元数据还可声明默认程序名与建议搜索目录 (~search_paths~)；建议目录可以通过程序内常量静态定义，Emacs 模块使用 ~EMACSCLIENT_SEARCH_PATHS~ ，随模块元数据返回。

#+begin_src json
{
  "key": "emacsclient_path",
  "data_type": "executable",
  "remote_access": "local",
  "default": null,
  "executable": {
    "default_program": "emacsclient",
    "search_paths": ["/opt/homebrew/bin", "/usr/local/bin", "/Applications/Emacs.app/Contents/MacOS/bin", "/Applications/Emacs.app/Contents/MacOS"]
  }
}
#+end_src

没有用户设置和静态 ~default~ 时，配置模块按 services 启动时的 ~PATH~ 顺序搜索，再按 ~search_paths~ 的顺序补充查找。只接受实际可执行的普通文件（允许符号链接），返回绝对路径；不通过 shell，不执行待查找的程序，也不展开 ~ 和环境变量。每次读取重新查找，因此安装或移除程序后，下次读取即可反映变化。找不到程序时不生成默认值，Emacs 配置界面显示“未设置”并提供文件选择入口。

配置项通过 ~remote_access~ 声明绑定设备的访问范围。~local~ 为默认值，~read~ 开放读取，~read_write~ 另开放替换、部分更新和预检。配置中心依据 network 注入的 ~x-loki-remote-devices~ 判断请求来源。远端元数据和模块值只包含可读项，直接访问受限项返回 403 ~remote-config-forbidden~ 。目前 ~network/relay_url~ 为只读，~control-center/center_auto_start~ 可读写，其余配置项仅限本机。

* 生效值与来源

~GET /data/{module_id}~ 中的每个值包含 ~value~ 和 ~source~ ：

#+begin_src json
{"module_id":"emacs","values":{"emacsclient_path":{"value":"/opt/homebrew/bin/emacsclient","source":"default"}}}
#+end_src

~GET /data/{module_id}/{key}~ 以及写入成功的响应保留模块和配置项标识，同时返回 ~value~ 与 ~source~ ：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","value":"/opt/homebrew/bin/emacsclient","source":"user"}
#+end_src

~source~ 只支持 ~user~ 与 ~default~。显式设置的值优先，即使与默认值相同也标记为 ~user~；否则返回静态默认值或发现的程序路径，并标记为 ~default~。未设置且没有默认值的项不出现在模块数据中，单项读取返回 404 ~config-not-set~。默认值中的 ~false~、~0~ 或空字符串均是有效值，不按真假判断是否存在。

~PUT~ 和 ~POST~ 的请求体仍为原始 JSON 值，不接收来源包装。字典合并或列表追加以当前生效值为基础，包括默认值，完成后整项标记为 ~user~ 。变更订阅只通知用户写入，自动发现的默认值不触发用户配置变更。

* 统一校验

~POST /config/validate~ 接受模块、配置项和待校验值，供客户端或其他程序使用：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","value":"emacsclient"}
#+end_src

接口与配置保存共用校验实现。~Executable~ 检查目标存在、是普通文件并具有执行权限，允许指向普通文件的符号链接。程序名先按服务进程 ~PATH~，再按元数据 ~search_paths~ 查找；有效值规范化为绝对路径。整个检查不会执行目标程序。

校验通过时返回 HTTP 200 与规范化后的值：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","valid":true,"value":"/opt/homebrew/bin/emacsclient"}
#+end_src

配置值无效时仍返回 HTTP 200，使用 ~valid: false~ 和错误说明表示预检结果：

#+begin_src json
{"module_id":"emacs","key":"emacsclient_path","valid":false,"error":{"source":"business","code":"invalid-config","message":"配置值无效：emacsclient 位置：文件不存在：/missing/emacsclient"}}
#+end_src

不存在的模块或配置项返回 404；内部错误使用对应 HTTP 错误码。预检不写入文件、不更新用户值，也不发出变化通知。~PUT /data/{module_id}/{key}~ 与部分更新会在提交时重新校验；校验失败返回 400 ~invalid-config~，已有内存值、YAML 文件与变化通知均不受影响。~Executable~ 保存成功时使用规范化后的绝对路径。预检通过不保证提交时仍有效，例如文件可能在两次请求之间被移除。

Emacs 配置界面以 Customize 风格的 widget 按模块展示名称、说明、类型化编辑控件及来源状态，按服务端结果将错误标红并保留输入；校验、逐项保存、批量保存、撤销编辑和刷新行为见 [[file:emacs.org::*服务配置管理][服务配置管理]]。托盘“设置”调用 ~POST /emacs/apps/open?app=config~ ，“日志”调用 ~POST /emacs/apps/open?app=logs~ 并打开 ~~/.assistant/loki-assistant.log.org~ ，应用加载、日志文件打开和窗口聚焦由 services 的 Emacs 模块负责；登录启动由 services 的控制中心模块在配置提交前处理。

* 现有提交前变化处理

当前实现使用模块处理器和变更订阅。配置项逐步迁移到声明式通知接入点。

业务模块通过 ~ConfigService::with_change_handler(module_id, handler)~ 注册 ~ConfigChangeHandler~ 。配置中心将 ~ConfigChange~ 交给当前模块，其中包含模块、配置键、操作、候选完整值、提交前生效值，以及包含候选值的模块配置快照。处理器可读取当前配置。持有提交锁的处理器调用链禁止递归发起配置提交。

| 操作 | 模块处理器 |
|------+------------|
| 完整值替换、字典合并、结构数组记录更新 | ~process~ |
| 列表追加、结构数组记录新增 | ~append_records~ |
| 结构数组记录删除 | ~remove_records~ |

全量替换列表时，若成员变化只有新增或只有删除，也调用对应的数组处理器。带主键的数组按主键识别成员，其他数组按值及出现次数识别成员。同时包含新增和删除的全量替换调用 ~process~ ，该方法可以比较新旧完整值。数组处理器的默认实现调用 ~process~ 。仅需校验或同步外部状态的模块可以实现 ~handle~ ，默认的 ~process~ 在 ~handle~ 成功后返回候选值。

普通提交按顺序取得最新值、校验候选值、等待模块处理器、校验处理器返回值、原子写入 YAML、更新内存并发布变更。模块处理器返回应保存的完整值，配置中心用该值更新模块快照和变更通知，也用它生成包含数据的 HTTP 成功响应。对于带主键的数组，处理器可以补充或规范化字段，记录主键集合须与候选值一致。

- 模块处理失败时返回 HTTP 500 ~config-change-rejected~ 。该提交不会改动 YAML、内存配置或发布变更。处理器负责撤销失败操作产生的部分副作用。
- 处理器返回的数据校验失败时，配置中心调用 ~rollback~ 并返回 ~config-change-rejected~ 。处理成功后发生写入失败时，同样调用 ~rollback~ 并返回 ~config-storage-error~ 。
- YAML 写入成功后，配置中心更新内存、广播变更并调用 ~committed~ 。此回调可切换模块运行状态，失败会写日志。~subscribe~ 和 ~subscribe_module~ 的接收方在提交完成后接收变更。
- 配置事务在服务端任务中执行。HTTP 请求断开后，已经接受的任务会继续执行。读取、预检和手动修改 YAML 均不执行模块处理器。

~password~ 类型由模块注册的凭据存储处理器完成写入。配置中心只返回是否已设置，用同一布尔标记发布变更，明文由模块管理。

* YAML 存储

用户配置保存到 ~~/.assistant/config.yml~ ，文件内容按模块和键组织，仅存用户值：

#+begin_src yaml
emacs:
  emacsclient_path: /opt/homebrew/bin/emacsclient
control-center:
  center_auto_start: false
#+end_src

文件缺失视为没有用户设置，首次成功写入时创建。保存使用权限为 ~0600~ 的同目录临时文件并原子替换目标文件；落盘成功后才更新内存和广播变化。并发写入按顺序处理，保存失败返回 HTTP 500 ~config-storage-error~ ，不覆盖已生效的内存配置。默认值、来源标签及静态元数据不写入 YAML。

启动时读取文件并校验当前已知配置项；文件损坏或已知值类型错误会阻止启动。其他版本或插件的未知配置保留在文件中，但不出现在当前模块数据里。手动修改 YAML 后重启 services 生效；通过 HTTP 修改则立即生效。~ConfigService::new~ 与 ~from_registry~ 提供无文件存储的实例用于测试，进程入口通过 ~Services::load~ 加载用户文件。

* 结构化配置

~GET /meta~ 的 ~modules[].items~ 描述配置值。~data_type: structure~ 表示一个 JSON 对象。~data_type: list~ 配合 ~list.item_type: structure~ 表示一个结构数组。~structure.fields~ 声明每个字段的 ~data_type~、~required~、可选默认值模板、校验器和候选项。Emacs 在统一配置页按这些定义生成表单。~id_field~ 可指定数组元素的主键，以便单独保存元素。没有主键的数组通过通用 ~POST /data/{module}/{key}~ 追加元素。

结构可声明 ~show_all_fields~ ，让 Emacs 在一条记录下显示所有字段。缺少值时显示「未设置」，密码字段显示保存状态。

校验器可声明 ~emacs_pattern~ ，用于 Emacs 本地输入格式提示。服务端保存时按 ~checker.pattern~ 和对应的业务规则处理。

配置项可声明 ~requires_local_auth~、~save_timeout_seconds~ 和 ~read_only~ 。只读配置项可查询生效值，通过配置 HTTP 接口提交写入、删除或写入预检时返回 ~403 config-read-only~ 。配置中心按模块 ID 和配置键合并 ~CONFIG_ITEMS~ 注册的元数据。客户端按字段声明填写必填值，并显示服务端返回的保存结果。

| 操作 | 请求 | 结果 |
|------+-------+------|
| 读取配置定义和值 | ~GET /meta~、~GET /data/{module}~ | 读取注册的结构和生效值 |
| 新增带主键记录 | ~PUT /data/{module}/{key}/{instance}~ 配合 ~If-None-Match: *~ | 返回 ~200~ 和保存记录，主键已存在时返回 ~412 config-record-exists~ |
| 修改带主键记录 | ~PATCH /data/{module}/{key}/{instance}~ | 合并指定字段，按通知结果返回 ~200~ 或 ~202~ |
| 删除带主键记录 | ~DELETE /data/{module}/{key}/{instance}~ | 返回 ~204~ 。记录已不存在时同样返回 ~204~ |
| 追加无主键元素 | ~POST /data/{module}/{key}~ ，请求体是数组 | 返回保存后的完整数组 |
| 修改或删除无主键元素 | ~PUT /data/{module}/{key}~ ，请求体是替换后的数组 | 返回保存后的完整数组 |

按字段修改和手动重试的契约见 [[*刷新配置与手动重试][刷新配置与手动重试]]。

* 结构中的密码字段

带主键的结构数组可使用 ~Password~ 类型。~data_type.password.path~ 是 pass 内相对的 ~.gpg~ 路径，~{key}~ 展开为当前记录的主键值。省略 ~data_type.password.key~ 时，该字段是首行的主密码。指定 ~key~ 时，该字段对应后续的同名行。配置和 HTTP 响应只保存条目引用。

#+begin_src json
[
  {"key":"token","data_type":{"password":{"path":"loki-assistant/slack/{key}.gpg"}}},
  {"key":"d_cookie","data_type":{"password":{"path":"loki-assistant/slack/{key}.gpg","key":"d_cookie"}}}
]
#+end_src

配置模块将共享条目的候选凭据暂存为一份加密条目。业务确认后，配置模块写入正式条目和配置引用，再清理候选条目。修改一项时保留同一条目中未修改的字段。显式清除首行字段会删除整份共享条目和各字段的引用。配置写入失败时，配置模块尝试恢复原条目。

* 配置项通知接入点

迁移后的配置项用元数据中的 ~notification_endpoint~ 替代模块处理器绑定和业务模块对配置变更的订阅。元数据给出 services 内部 HTTP 路径，业务模块负责该路径的处理及状态查询。配置模块按声明调用接口。

通知接入点可配置在单个值或带主键的结构数组上。单值配置直接以该值作为 ~key~ 。结构数组的元素须指定一个必填的 ~Key~ 类型字段，元数据中表示为 ~"data_type": "key"~ 。字段值是记录主键，在数组内唯一且创建后固定。配置模块将 ~key~ 编码为一个路径段并追加到接入点，形成 ~{notification_endpoint}/{key}~ 。

** 写入与确认

1. 配置模块用通用写入接口校验并保存待确认的值或记录。状态由配置模块管理，业务读取使用已确认的数据。
2. 配置模块发送 ~POST {notification_endpoint}/{key}~ 。单值的请求体为原始 JSON 值。结构数组的请求体为该记录的数据字段，例如 ~{"date1":1}~ 。~Password~ 字段由业务模块通过配置模块内部读取。
3. 配置模块根据通知响应确认或回退这次写入。

| POST 结果 | 配置模块处理 |
|-----------+--------------|
| ~200~ 或 ~204~ | 将待确认的值或记录切换为已确认。业务模块可返回结构数组记录的只读字段，配置模块校验后随记录一并保存。 |
| ~202~ | 保留待确认状态，等待业务模块完成处理。 |
| ~422~ 携带内部 ~NotificationValidationError~ | 持久化候选记录及错误，~pending[].status~ 为 ~invalid~ 。业务模块可要求清除候选记录的指定密码字段，响应头 ~X-Loki-Config-Cleared-Fields~ 列出这些字段。后续 ~PATCH~ 可重新提交。 |
| 其他明确的错误响应 | 回退本次写入及对应的凭据变更。替换单值失败时保留原有已确认值。 |

业务模块异步处理后更新本次写入的状态。结果为处理中或未知时，配置模块保留待确认变更，供后续手动重试。

** 删除通知

配置模块标记删除待确认，向同一接入点发送 ~DELETE {notification_endpoint}/{key}~ 。单值使用删除前的值，结构数组使用待删除记录的 ~Key~ 字段。成功后移除数据，失败时保留原记录。返回 ~202~ 时保留待确认状态，等待手动重试。 [[file:slack-development.org::*Team 注册流程图][Slack 接入流程]]

** 刷新配置与手动重试

手动重试复用配置资源的 ~PUT~ 接口。单值使用 ~PUT /data/{module}/{key}~ ，带主键的记录使用 ~PUT /data/{module}/{key}/{instance}~ 。配置模块根据 ~module~ 和 ~key~ 找到配置项元数据中的 ~notification_endpoint~ ，并根据 ~instance~ 定位结构数组中的记录。发送业务通知时，结构数组用记录的主键作为通知路径中的键，单值用待确认变更保存的值作为键。

| 请求 | 语义 |
|------+------|
| ~PUT~ ，请求体为零字节 | 重新触发该资源当前的待确认变更，复用其中保存的参数。 |
| ~PUT~ ，请求体为 ~{}~ ，带 ~If-None-Match: *~ | 新增仅含路径主键的记录，按元数据校验必填字段。 |

用 ~PATCH /data/{module}/{key}/{instance}~ 修改带主键记录的字段，单个结构对象使用 ~PATCH /data/{module}/{key}~ 。请求体为 ~application/merge-patch+json~ 的 JSON 对象。~{"name":"X-Tech"}~ 设置名称，~{"name":null}~ 清理可选名称，省略字段则保留原值。清理必填字段或修改主键返回校验错误。已有待确认变更时，以待确认数据为基础合并字段，否则以生效记录为基础。

用 ~PATCH~ 明确表达局部修改，客户端只提交它拥有新值的字段，可减少覆盖其他字段和重新传输凭据的问题。~PUT~ 适合按已知主键创建记录或设置整个单值。代价是客户端需要按操作选择 HTTP 方法，服务端需要支持两种请求。单值配置的参数名由路径中的 ~key~ 指定，设置时提交 JSON 值，清理时使用该项的 ~DELETE~ 接口。

手动触发沿用原配置项的写入权限与本机鉴权。配置模块按资源路径查找当前的待确认变更，使用已保存的数据和原通知接入点再发送一次通知。待确认的写入发送 ~POST~ ，待确认的删除发送 ~DELETE~ 。同一变更只允许一个通知请求在途，包括首次通知。变更 UUID 由配置模块内部传递，业务模块用它识别原变更。配置模块只应用与当前待确认变更 ID 匹配的结果。

| HTTP 结果 | 处理 |
|-----------+------|
| ~200~ | 业务确认后提交变更，返回 ~{"api_version":"1","status":"confirmed"}~ 。 |
| ~202~ | 业务仍在处理或响应结果未知，返回 ~{"api_version":"1","status":"pending"}~ 。 |
| ~404 config-pending-not-found~ | 此资源没有待确认变更。 |
| ~409 config-retry-in-progress~ | 同一次变更已有通知请求在途。 |
| ~422~ | 业务报告明确的校验错误，候选数据和错误保留供后续编辑。 |
| ~500 config-change-rejected~ | 业务明确拒绝，配置模块回退本次变更并返回错误。 |

返回 ~202~ 后，下一次业务通知由手动重试触发。对于异步业务，接入点在收到相同 ID 的通知时返回该次处理的最新状态。Slack 的 ~POST~ 接入点在凭据齐全后校验，缺少凭据时打开工作区配置页。 [[file:slack.org::*Team 配置][Slack 工作区配置]]
