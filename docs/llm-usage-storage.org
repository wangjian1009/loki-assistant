#+TITLE: LLM 用量记录与长期存储设计

* 范围

本文说明当前用量存储、查询和 Emacs 界面，以及待实现的进程退出设计。当前运行接口见 [[file:control-center-services.org::*AI 统一代理][AI 统一代理]]。由 ~modules/llm~ 内独立的 Tokio task 接收转发事件、解析用量、写入明细和定期聚合。转发路径负责发送观测事件，继续按请求转发原始响应。选用单个 SQLite 数据库，使用 WAL 和批量事务。数据库操作由统计任务串行安排到阻塞线程，查询使用短时 SQL 语句。明细是长期保存的数据，日报是可重建的查询结果。

* 转发与统计任务

| 事件 | 发送时机 | 字段 |
|------+----------+------|
| ~Started~ | 选定上游后 | Loki 请求 ID、客户端 ID、可选会话标识、实际上游 ID、协议、开始时间、请求方法及路径后缀 |
| ~Headers~ | 收到上游响应头 | 请求 ID、HTTP 状态及观察所需的 ~Content-Type~ 和 ~Content-Encoding~ |
| ~BodyBytes~ | 转交响应正文数据块时 | 请求 ID、原始数据块 |
| 请求模型 | 转发请求正文时 | 请求 ID、逐块识别的顶层 ~model~ |
| ~Finished~ | 正文读完、上游失败或客户端断开 | 请求 ID、结束时间、结果、首包及总耗时、观测是否缺段 |

- 转发入口用 ~mpsc::Sender::try_send~ 投递响应数据块。控制事件和正文观测进入同一任务队列。正文额度不足时只停止投递这一请求后续的正文观测。请求守卫在正常返回或被取消时发送一次 ~Finished~ ，统计任务先处理已经投递的正文，再处理终态。
- 正文观测队列的字节预算为 16 MiB，每条正文消息至少占 64 字节额度。统计任务处理数据块后释放额度。额度不足时，该请求继续转发，终态将用量标记为不完整。
- 统计任务解析 JSON、Chat Completions SSE、Responses SSE 和 Claude SSE。模型优先采用响应中的 ~model~ ，也可从请求流识别顶层 ~model~ 。SQLite 保存提取的 ~usage~ 、可选模型名和请求元数据。请求详情由独立文件缓存提供。
- 用量缺字段、传输中断或观察缺段时，终态保留已知数值并标记 ~incomplete~ 。缺失字段存 ~NULL~ ，明确上报的零存 ~0~ 。传输结果与用量完整性各用独立字段。供应商归属固定为请求开始时的选路结果。
- Tokio task 负责接收、组批、定时和恢复调度。SQLite 同步 I/O 在 ~spawn_blocking~ 中串行执行，由同一个 task 调度唯一写连接。查询与写入共享串行数据库连接。当前退出流程会提交已入队的批次，完整排空时序见 [[*进程退出][进程退出]]。

* 存储结构

数据库位于 =~/.assistant/llm-usage.sqlite3= 。~usage_event~ 仅追加，每个达到终态的已登记推理请求对应一行，重复请求 ID 保留首条已提交记录。输入 token 规范化为三个互斥分项 ~input_uncached_tokens~、~cache_read_tokens~ 和 ~cache_write_tokens~ 。OpenAI 兼容接口的缓存读取包含在输入中，归一化时扣除一次。Claude 的缓存读写独立上报。~raw_usage_json~ 只存上游报告的用量字段，以便公式变化后重算。请求和响应均未提供可用模型名时，索引列使用空字符串表示未知分组。

明细存 UTC 毫秒，以请求完成时间归入报表日。日报用固定报表时区计算 ~report_day~ ，首版默认 ~Asia/Shanghai~ 。日期过滤使用左闭右开区间，便于分页和跨日拼接。~input_reported_tokens~ 保存上游原始输入计数，供旧接口保持统计口径。~normalization_version~ 记录单行用量采用的归一化版本。

#+begin_src sql
CREATE TABLE usage_event (
    seq INTEGER PRIMARY KEY,
    request_id TEXT NOT NULL UNIQUE,
    client_id TEXT NOT NULL,
    session_id TEXT,
    upstream_id TEXT NOT NULL,
    protocol TEXT NOT NULL,
    model TEXT NOT NULL,
    started_at_ms INTEGER NOT NULL,
    finished_at_ms INTEGER NOT NULL,
    report_day TEXT NOT NULL,
    outcome TEXT NOT NULL,
    upstream_status INTEGER,
    first_byte_ms INTEGER,
    duration_ms INTEGER NOT NULL,
    input_reported_tokens INTEGER,
    input_uncached_tokens INTEGER,
    cache_read_tokens INTEGER,
    cache_write_tokens INTEGER,
    output_tokens INTEGER,
    incomplete INTEGER NOT NULL CHECK (incomplete IN (0, 1)),
    raw_usage_json TEXT,
    normalization_version INTEGER NOT NULL
) STRICT;

CREATE INDEX usage_event_time
    ON usage_event (finished_at_ms DESC, seq DESC);

CREATE INDEX usage_event_client_upstream_time
    ON usage_event (client_id, upstream_id, finished_at_ms DESC, seq DESC);

CREATE INDEX usage_event_client_session_time
    ON usage_event (client_id, session_id, finished_at_ms DESC, seq DESC)
    WHERE session_id IS NOT NULL;

CREATE TABLE usage_daily (
    report_day TEXT NOT NULL,
    client_id TEXT NOT NULL,
    upstream_id TEXT NOT NULL,
    protocol TEXT NOT NULL,
    model TEXT NOT NULL,
    requests INTEGER NOT NULL,
    incomplete_requests INTEGER NOT NULL,
    input_reported_tokens INTEGER NOT NULL,
    input_uncached_tokens INTEGER NOT NULL,
    cache_read_tokens INTEGER NOT NULL,
    cache_write_tokens INTEGER NOT NULL,
    output_tokens INTEGER NOT NULL,
    PRIMARY KEY (report_day, client_id, upstream_id, protocol, model)
) STRICT, WITHOUT ROWID;

CREATE TABLE usage_checkpoint (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    through_seq INTEGER NOT NULL
) STRICT;

INSERT INTO usage_checkpoint (id, through_seq) VALUES (1, 0);

CREATE TABLE usage_meta (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    data_from_ms INTEGER NOT NULL,
    legacy_json TEXT NOT NULL
) STRICT;
#+end_src

日报数值是各分项已知值之和，~incomplete_requests~ 提示该行存在未完整计量的请求。请求完成后才生成明细。模型列表和 token 估算仍可进入运行监控。它们的接口调用独立于推理用量聚合。

下面两条明细的输入总量相同。OpenAI Responses 上报的 120 个输入已经包含 80 个缓存读取，Claude 分别上报 30 个未缓存输入、80 个缓存读取和 10 个缓存写入。

| 协议 | 原始输入 | 未缓存输入 | 缓存读取 | 缓存写入 | 输出 |
|------+----------+------------+----------+----------+------|
| Codex | 120 | 40 | 80 | 0 | 10 |
| Claude | 30 | 30 | 80 | 10 | 10 |

在 OpenAI Responses 的归一化规则中，协议无独立缓存写入字段，该分项计为 ~0~ 。其他未上报且无法确定的分项保存为 ~NULL~ 。~raw_usage_json~ 保存对应协议实际返回的用量字段，例如 OpenAI 的 ~input_tokens_details.cached_tokens~ 。历史明细只保留采集到的用量字段、请求元数据和上游 ID，系统指令通过实时请求详情查询。

* 增量写入、合并和保留

1. 统计任务达到 128 条终态记录或最旧记录等待 250 ms 时提交事务。写连接使用 WAL 和 ~synchronous=FULL~ ，将落盘开销分摊到批次。重复 ~request_id~ 用 ~ON CONFLICT(request_id) DO NOTHING~ 处理。数据库暂时不可写时保留待提交批次，后续定时与查询尝试重新提交，并在查询响应中报告存储错误。
2. 定时器每 60 秒合并一批，并在启动时补做。单次事务读取水位 ~through_seq~ ，取至多 10,000 条更大的 ~seq~ ，按日报主键组合聚合后 ~UPSERT~ ，再将水位推进到本批最大 ~seq~ 。聚合和推进水位同事务提交，断电后重跑有同样的汇总结果。迟到明细使用它自己的日期，仍由更大的 ~seq~ 纳入合并。积压由后续小批次追赶，期间可继续提交新明细。
3. 长期保留明细和原始用量字段。SQLite 执行常规 WAL 检查点，日报使用增量合并。

** 实时请求

~GET /llm/requests~ 从用量任务读取一次快照。~active~ 按开始时间列出在途请求，首包到达前的 ~phase~ 为 ~waiting~ ，首包到达后为 ~responding~ 。在途请求的 ~usage~ 为 ~null~ 。

~recent~ 合并待落盘记录和 SQLite 已落盘明细，按完成时间倒序返回最近 100 条已结束的推理请求。~phase~ 为 ~completed~ 、 ~failed~ 或 ~cancelled~ 。~usage~ 包含上游上报口径的 ~input_tokens~ 、 ~output_tokens~ 及完整标记 ~complete~ ，缺失的计数为 ~null~ 。~storage_error~ 表示最近一次落盘失败。此查询为只读操作。

~has_detail~ 表示对应请求的缓存文件可用。实时列表只查询这个状态，需要查看正文时按 ID 查询详情。

** 请求详情缓存

配置中心的「AI 统一代理」模块提供三个独立配置项。

| 配置项 | 用途 |
|--------+------|
| ~monitoring_filter~ | 当前过滤条件，默认 ~{}~ |
| ~monitoring_history~ | 最近使用的过滤条件，最多 10 条 |
| ~monitoring_retention~ | 已完成请求的详情缓存保留条数，默认 500，可设为 0 |

过滤条件支持协议 ~protocols~ 、客户端 UUID ~clients~ 和供应商 ID ~upstreams~ ，每个字段为数组。所有条件为空时关闭详情采集。至少一个维度有值时开启采集。每个已填写的维度都需要匹配，同一维度内任一值匹配即可。采集范围在请求开始时确定，已有缓存继续按保留条数清理。

例如以下组合仅采集指定客户端发往 ~work~ 或 ~personal~ 的 Codex 请求。

#+begin_src json
{"protocols":["codex"],"clients":["1c30befd-aacd-419b-b0f3-8d72680d275b"],"upstreams":["work","personal"]}
#+end_src

~GET /llm/monitoring~ 返回 ~filter~ 和 ~history~ 。~PATCH /llm/monitoring~ 接受 ~{"filter":{...}}~ ，传 ~{"filter":{}}~ 取消过滤器。快捷设置的非空过滤器会写入历史，按最近使用顺序去重。历史和保留条数可在配置中心独立编辑。

命中范围的请求在 =~/.cache/assistant/llm/requests/= 下按 ID 各建一个文件，转发过程中依次追加元数据、请求与响应分块。写入按收到的分块进行，详情采集没有单条正文体积上限。启动时和每 60 秒按请求开始时间清理旧文件，默认保留最近 500 条，仍在写入的文件等请求结束后的后续清理。缓存保留期间可以在服务重启后继续按 ID 查询。

~GET /llm/requests/{id}~ 返回 ~item~ 。已采集时，~item.instructions.blocks~ 按请求顺序返回，每段包含字段路径 ~source~ 、角色 ~role~ 和原文 ~text~ 。Responses 从 ~instructions~ 和 ~input~ 中提取，Chat Completions 从 ~messages~ 中提取 ~system~ 和 ~developer~ 角色，Claude Messages 从顶层 ~system~ 提取。缓存缺失或已清理时返回 HTTP 404。

~item.request_content~ 包含请求参数 ~settings~ 、工具定义 ~tools~ 和按顺序排列的输入 ~blocks~ 。~item.response_content~ 包含响应块 ~blocks~ 和完整性标记 ~complete~ 。块以 ~kind~ 区分消息、工具调用、工具结果和上游错误，可携带 ~role~ 、工具名 ~name~ 、调用标识 ~id~ 和正文 ~text~ 。SSE 响应在读取详情时按序还原。工具结果在客户端把结果发回代理或上游提供执行结果时可见。结构化视图用类型表示图片、文件和音频。~GET /llm/requests/{id}/raw/{part}~ 按 ~request~ 或 ~response~ 流式返回原字节，也可取出压缩正文。详情和原始正文均限本机读取，响应带 ~Cache-Control: no-store~ 。

** 历史请求

~GET /llm/usage/requests~ 接受下列参数。多个筛选条件同时生效。

| 参数 | 含义 |
|------+------|
| ~from~ 、 ~to~ | 按请求完成时间筛选，格式为 RFC 3339，精度到毫秒，含 ~from~ ，到 ~to~ 前为止。可单独传入。 |
| ~client_id~ 、 ~upstream~ 、 ~protocol~ 、 ~model~ | 按客户端 UUID、实际供应商 ID、协议或所记录的模型名精确匹配。~protocol~ 为 ~codex~ 或 ~claude~ 。 |
| ~session_id~ | 精确匹配客户端原生会话标识，同时传入 ~client_id~ 。 |
| ~outcome~ 、 ~incomplete~ | 结果为 ~completed~、~failed~ 或 ~cancelled~ 。~incomplete~ 为 ~true~ 或 ~false~ 。 |
| ~limit~ 、 ~cursor~ | 每页默认 50 条，允许 1 至 100 条。后续页原样传回 ~next_cursor~ ，沿用原筛选条件。 |

明细按 ~finished_at_ms DESC, seq DESC~ 排序。第一页在读事务内取得当时的最大 ~seq~ 。游标包含这次查询的最大 ~seq~ 、末条结果的完成时间和序号，以及筛选条件的摘要。后续页将 ~seq~ 限制在首次查询水位内，并从末条结果之后继续读。新插入的记录即使完成时间较早，也会在下一次从第一页查询时出现。~next_cursor~ 为 ~null~ 表示已到末页。

明细的输入计数同时提供上游口径 ~input_reported_tokens~ 和归一化后的未缓存输入、缓存读写。时间使用 UTC RFC 3339 表示。未知计数或会话标识返回 ~null~ 。单条查询返回 ~item~ 和同一条记录的 ~raw_usage~ ，其值为提取出的上游用量对象或 ~null~ 。列表响应省略 ~raw_usage~ 。

历史列表和单条详情按 ~client_id~ 返回当前配置中的 ~client_name~ 。找不到客户端配置时名称为 ~null~ ，界面显示「未知客户端」。

** 日报与月报

~GET /llm/usage/summary~ 接受 ~from_date~ 和 ~to_date~ ，按数据库的报表时区解释 ~YYYY-MM-DD~ 日期，含起始日、到结束日期前为止。默认查询截至当天的 30 个自然日。显式指定区间时同时提供两个日期。~bucket~ 取 ~day~ 或 ~month~ ，默认为 ~day~ 。月分组按月初日期标识，区间边缘仅计入请求的日期。~group_by~ 可选 ~client_id~、~upstream~、~protocol~ 或 ~model~ 。省略时每个日期分组只返回一行。

日报接受与明细相同的 ~client_id~、~upstream~、~protocol~、~model~ 和 ~session_id~ 筛选。带会话标识时，使用会话索引查询该客户端的明细并按时间汇总。没有标识的请求仍计入普通日报。

~items~ 按 ~period_start~ 和分组值升序排列，有记录的日期分组才生成行。省略分组维度时，~group_by~ 和各行的 ~group~ 返回 ~null~ 。按模型分组时，未知模型的 ~group~ 也为 ~null~ 。~totals~ 汇总选定区间内全部匹配记录，计数为已知值之和，~incomplete_requests~ 表示其中有多少条用量不完整。响应包含 ~time_zone~ 、实际查询区间和 ~bucket~ 。~data_from~ 为数据库记录的历史明细采集启用时间，用于解释迁移前的空白。~storage_error~ 表示最近一次写入失败。

  "to_date": "2026-11-26",

  "bucket": "day",
  "group_by": "upstream",
  "items": [

      "period_start": "2026-11-25",

日历筛选、聚合维度或游标无效时返回标准 ~400~ 错误 ~llm-invalid-usage-query~ 。合法筛选无匹配时返回 ~200~ 、空 ~items~ 和适用的零值总计。单条请求 ID 无效时返回 ~400~ ，没有对应记录时返回 ~404 llm-usage-request-not-found~ 。读取存储失败时返回 ~503 llm-usage-unavailable~ 。

** 筛选候选

~GET /llm/usage/options~ 按 ~dimension~ 返回可选值，支持 ~client_id~ 、 ~upstream~ 和 ~model~ 。~source~ 默认为 ~history~ ，从历史明细中读取，可传入与历史请求一致的 ~from~ 、 ~to~ 、 ~client_id~ 、 ~upstream~ 、 ~protocol~ 和 ~model~ 限定范围。推荐调用时省略正在编辑的维度。~source=sessions~ 从会话累计记录及已导入的会话期初余额中读取客户端或供应商，可传入另一维的精确值限定范围。协议、结果和用量完整性选项使用接口已定义的枚举。

候选去重后按值升序返回。可选参数 ~q~ 按前缀查找，~limit~ 默认为 30，范围为 1 至 100。响应示例如下。~has_more~ 为 ~true~ 时，控件提示继续输入以缩小范围。历史中已经撤销的客户端和已移除的供应商仍可作为筛选值。

#+begin_src json
{
  "api_version": "1",
  "items": [{"value": "openai"}, {"value": "backup-openai"}],
  "has_more": false
}
#+end_src

~value~ 直接用于精确筛选。用量列表和客户端筛选候选响应提供 ~client_names~ ，其键为客户端 UUID，值为当前配置中的名称。Emacs 在汇总、请求、详情及筛选控件中使用名称显示，查询仍使用 UUID。找不到名称的记录显示「未知客户端」。未知模型在报表中单列为「未知模型」，其余可筛选模型均来自有效模型名。

** 会话累计查询

~GET /llm/usage/sessions~ 增加可选精确筛选 ~client_id~ 、 ~upstream~ 和 ~session_id~ 。指定 ~session_id~ 时同时提供 ~client_id~ 。用量按客户端、会话和实际供应商分别返回，包含旧会话期初余额。响应沿用现有 ~usage~ 数组，用量字段使用上游口径。界面的「查看请求」将该行的客户端、会话和供应商值传给历史请求接口。

界面请求传入 ~limit~ 以分页，默认使用 50 条，允许 1 至 100 条。分页顺序为 ~client_id~ 、 ~session_id~ 、 ~upstream~ 升序。返回 ~next_cursor~ ，客户端用它继续查询并沿用原筛选条件。省略 ~limit~ 和 ~cursor~ 时沿用当前全量响应。

** 读取路径与旧数据

- 历史列表使用时间索引或带客户端、上游或会话条件的复合索引，按游标定位。单条请求通过唯一 ~request_id~ 查找。历史候选沿用时间条件，查询请求的维度列并去重，按实际执行计划补充索引。
- 日报和月报在同一短时只读事务中读取 ~usage_daily~ 及水位 ~through_seq~ ，加上过滤后 ~seq > through_seq~ 的明细尾部。已落盘的记录直接进入查询，下一次聚合将尾部转入日报。按会话查询使用原生会话标识，直接从会话索引聚合。
- 首次写入数据库元数据时，将旧 JSON 冻结为 ~usage_meta.legacy_json~ 。启动时分别从旧累计值和新明细恢复总量及会话用量。日报、月报及历史请求从首条新明细起计算。累计接口的 ~input_tokens~ 继续对应上游上报值。

* 进程退出

~main.rs~ 统一处理 ~SIGTERM~、~Ctrl-C~ 和 HTTP 服务异常返回。当前本机 Homebrew LaunchAgent 的 ~exit timeout~ 为 5 秒，方案以收到退出信号时的单调时钟为起点，内部总预算为 4 秒。以下时序为待实现设计。

1. *先发退出消息。* 关闭新请求的准入，触发 Axum 的 ~with_graceful_shutdown~ 。通过独立控制通道向统计 task 发送 ~Shutdown~ 和确认发送端，同时通知网络入口和扩展任务停止接收或启动新工作。统计 task 收到 ~Shutdown~ 后进入排空阶段，继续接收已登记请求的 ~BodyBytes~ 和 ~Finished~ 。控制消息使用一次性通道，观测队列即使已满也能收到退出通知。
2. *再限时等待。* 已进入的 HTTP 请求最多继续运行 2.5 秒。Axum 停止接受新连接，准入检查拦住已有连接或中转入口尝试发起的新业务请求。达到 2.5 秒时，取消仍在等待上游响应头或转发正文的请求，并关闭对应上游连接。取消通过请求守卫使用已预留的槽位投递 ~Finished~ 。终态记为 ~cancelled~，保留已提取的 token，未取得完整用量则标记 ~incomplete~ 。
3. *封口并提交。* 等待所有已登记观测的生产者释放请求守卫后，通过一次性通道通知统计 task 可以关闭接收端。task 排空已入队事件，提交最后一批 ~usage_event~ ，关闭写连接，然后发送落盘确认。日报合并任务进入退出流程后不再启动，未合并的已提交记录由下一次启动从 ~through_seq~ 补做。网络和扩展的停止确认在同一全局预算内并行等待。
4. *收尾并退出。* HTTP 和后台任务结束、统计落盘得到确认后，删除当前进程拥有的服务信息文件，刷出退出日志，再释放实例锁。HTTP 服务异常或最后一批写盘明确失败时记录失败原因，并返回非零退出状态。所有阶段共用同一个截止时间。

取消等待某个 Future 可能只结束等待方，Axum 的连接任务及 ~spawn_blocking~ 中的 SQLite 调用仍可能运行。因此首版计划由独立于 Tokio runtime 的看门狗执行 4 秒硬截止。发出退出通知后启用看门狗，正常收尾完成后解除。到期时以非零状态终止进程，由操作系统释放监听端口和实例锁。已提交事务由 SQLite WAL 恢复。尚未提交的明细可能丢失，下一次启动会覆盖可能残留的服务信息文件。硬截止保障收尾耗时，正常退出以统计 task 的提交确认为准。

验证使用临时端口、临时数据库和模拟上游。短 SSE 在退出消息后继续到终态，核对用量持久化。长 SSE 到期取消，核对已取得的部分用量和终态。队列塞满时退出消息仍应送达。模拟 SQLite 写入卡住时进程应在硬截止内退出，重启后核对已提交明细、水位与退出状态。

* 本机样本验证

用 SQLite 3.54.1 写入 100 万条模拟明细，包含 16 个客户端、8 个上游和 5 个模型。完成日报合并并截断 WAL 后数据库约 343 MiB。热缓存下，按客户端和上游读取 50 条明细平均约 0.036 ms，单月汇总查询平均约 3.9 ms。这些是直接执行 SQL 的本机样本结果，样本采用加入会话列和会话索引前的表结构。

查询计划确认明细经复合索引定位，日报和尾部明细分别经日期主键和 ~seq~ 主键查找。样本中重复插入同一请求、合并回滚、重复合并，以及读取尚未合并的明细，均得到相同总量。
